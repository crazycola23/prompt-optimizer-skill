# 档位改写规范（Tier Guidance）

> **本文件所有条目都是"写进优化后提示词的内容"，不是本模式自身的行为准则。**
> 档位由用户选择；用户没给时默认按**主力模型**改写，并在交付开头标注一行。

## 0. 为什么按档位，而不是按型号

- 型号半年一换，档位不变。多数情况下，同一档位内不同厂商的模型对同一种写法反应相近。
- 规律只有一条：**模型越弱，越要把不确定性消掉；模型越强，越要少写步骤、多写目标。**
- 档位由用户对齐自己的供应商定价页或榜单，本文件不绑定任何厂商。

## 1. 三个档位

| 档位 | 特征 | 常见命名 |
|---|---|---|
| **便宜模型** | 低延迟低成本、上下文小、指令遵循弱、容易跑偏或漏做 | 各家 `mini` / `flash` / `lite` / `small` 级、小参数开源模型 |
| **主力模型** | 日常默认，能力与成本平衡，能完成多数多步任务 | 各家标准版 |
| **顶级模型** | 最强推理与长任务能力，最贵最慢，倾向过度工程与啰嗦 | 各家 `reasoning` / `pro` / 旗舰级 |

用户给出**具体型号**时：先把它归到某一档，再套该档规范；归类依据是厂商定价页或榜单上它相对同族模型的位置。拿不准就按更弱的一档写（更明确通常不会吃亏）。

---

## 2. 便宜模型：把不确定性全部消掉

| 检查项 | 怎么写进提示词 |
|---|---|
| 任务拆小 | 一条提示词只做一件事；多步任务拆成多次调用，后一次带上前一次的输出 |
| 步骤写全 | 用编号步骤写死流程，不写"视情况自行判断" |
| 规则代替判断 | 把判断改成可执行规则：`如果 A 则 B，否则 C`，别让它权衡 |
| 示例给足 | 3–5 个，覆盖边界情况——**这一档示例收益最大**。每例压到 2–3 行，示例总行数不超过提示词正文（规则+格式）的行数；超过就先精简示例本身 |
| 输出格式写死 | 给模板 / XML 骨架 / JSON 骨架，并写 `输出仅包含 X 本身`（用正向表述，例如"输出仅包含这个 JSON 数组"而不是"不要输出任何解释"） |
| 上下文精简 | 只贴相关片段；长文档先切分再逐段处理，别整篇塞进去 |
| 收敛范围 | 删掉"尽可能多""超出基础"这类开放式要求，改成明确清单 |
| 不要写自检指令 | 不写"检查你的答案""再核对一遍"，改用外部校验：格式校验、正则、失败重试 |
| 正向表述优先 | 它通常更照字面执行，`用流畅散文作答` 优于 `不要用 markdown` |
| 别要推理过程 | 不要求它输出思考步骤或理由，只要求结果 |
| 缩短单次输出 | 要求"每条不超过 N 字""只列 5 条"，长输出容易发散 |
| 脚手架 | 可以保留少量加强语（`必须` / `只`），但一条提示词里不超过两处 |

## 3. 主力模型：标准做法

- **清晰直接 + 给动机**：每条硬约束后补一句为什么，它能据此泛化。
- **结构化分区**：指令 / 上下文 / 示例 / 输入各用 XML 标签，避免互相污染。
- **编号步骤**：顺序或完整性重要时用编号列表，否则写成一段流畅要求即可。
- **示例 2–3 个**：相关、多样、用 `<example>` 包裹。
- **输出格式用正向描述**：写清"要什么"，必要时给模板。
- **篇幅**：按需，除非有硬性字数或条数要求才写死。
- **脚手架**：常规措辞即可，不必堆加强语，也不必刻意删净。
- **上下文安排**：长资料在前、提问与指令在后。
- **有限自主**：允许它在边界内自行判断，同时把边界写出来。
- **自检**：默认不加；仅当任务有可自动校验的成功标准（测试、schema、格式）时加一条"完成前对照标准核对"。
- **一次可做多步任务**，不必过度拆解。

## 4. 顶级模型：写目标，不写步骤

| 检查项 | 怎么写进提示词 |
|---|---|
| 给目标与成功标准 | 写清要什么结果、怎么算做对了；**步骤交给它自己规划** |
| 概括性思考指令 | `think thoroughly` 这类概括指令通常优于手写分步计划，它的推理往往超过人类预设 |
| 删脚手架 | 删掉为弱模型写的加强语（`CRITICAL` / `You MUST` / `If in doubt, use X`）——多数情况下会过度触发 |
| 删自检与复核 | 删掉 `double-check` / `include a final verification step`，它自己会验证，叠加通常只烧 token |
| 显式要求简洁 | 这一档默认啰嗦；写清篇幅、语气、是否要免责声明、长文是否要填充章节 |
| 显式要求进度更新 | 部分顶级模型在长工具链里过于沉默，要明确要求中间更新与结尾结论 |
| 显式限界 | 用正向边界表达范围：写"改动限定在 X 之内"，并说明哪些算超出范围；成串的"不要"要改写成正面表述 |
| 高自主 + 状态外置 | 长任务给自主性，状态写进文件（JSON / 进度笔记 / git），而不是写逐步指令 |
| 不可逆操作确认 | 删除、force push、对外发布、改共享设施前先问 |
| 子代理边界 | 写清何时该并行委派、何时该自己做，否则会滥用或该用不用 |
| 上下文安排 | 同主力（长资料在前）；多文档可要求先引用原文再作答 |
| 输出格式 | 给形态要求（篇幅、结构、语气），具体排版可交给它 |
| 示例 1–2 个即可 | 靠指令就能泛化，示例过多反而限制它 |
| 逃生口 | 给"如果发现前提本身是错的"这类分支一个明确出口，避免它为了满足成功标准而硬凑 |

---

## 5. 同需求三档对照

> 占位约定：本文示例统一使用 `[方括号]` 占位（如 `[REPORT]`、`[SECTION_3]`），**不使用 `{{ }}`**。其他参考文件里若出现 `{{ }}` 写法，改写时统一换成方括号；同一提示词内不要混用。若你要把提示词放进 `.format()` / Jinja 等模板引擎，注意示例中的 JSON 花括号需要转义。

### 例 A（分析类）：读一份 30 页季度报告，输出 10 条关键结论

**便宜档** —— 切分输入、写死格式、给足示例

```text
<task>阅读我给你的这几个 <section>，提炼可核对的关键结论。</task>
<rules>
1. 本提示词一次只处理我提供的这几个 <section>；我会分批把全部段落发给你。
2. 逐段处理：每段先判断是否包含可量化或可核对的事实（数字、日期、明确结论）。
3. 含事实的段，提炼 1 条结论，结论里必须带上原文出现的数字或日期，每条不超过 40 字。
4. 不含事实的段直接跳过，不产生条目。
5. 全部处理完后，把结论合并成一个 JSON 数组。
6. 最多输出 10 条；不足 10 条就少给，不要凑数。
</rules>
<output_format>
输出仅包含一个 JSON 数组本身，形如 [{"no":1,"point":"结论文本","source_section":"1"}]
</output_format>
<examples>
<example>输入：<section id="1">Q3 营收 4.2 亿元，同比增长 18%。</section>
输出：[{"no":1,"point":"Q3 营收 4.2 亿元，同比增长 18%","source_section":"1"}]</example>
<example>输入：<section id="2">管理层预计下季度毛利率提升约 1pct。</section>
输出：[{"no":2,"point":"管理层预计下季度毛利率提升约 1pct","source_section":"2"}]</example>
<example>输入：<section id="3">本季度团队士气良好，协作顺畅。</section>
输出：（该段不进数组）</example>
</examples>
<document>
<section id="1">[SECTION_1]</section>
<section id="2">[SECTION_2]</section>
<section id="3">[SECTION_3]</section>
</document>
```

**主力档** —— 结构化 + 引用锚定 + 给动机

```text
<role>你是一名财报分析师，为投资委员会准备简报。</role>
<documents>
  <document index="1">
    <source>quarterly_report.pdf</source>
    <document_content>
      <section id="1">[SECTION_1]</section>
      <section id="2">[SECTION_2]</section>
      <section id="3">[SECTION_3]</section>
    </document_content>
  </document>
</documents>

<task>
第一步：找出报告中与"营收、利润、现金流、风险"直接相关的原文段落，逐条列出并附上 section id。
第二步：基于这些引用，给出 10 条以内关键结论，每条注明来自哪个 section id。
</task>
<output_format>
用两段输出：先一段 `quotes`（每条一行，格式：`section id — 原文摘录`），
再一段 `conclusions`（每条一行，格式：`结论 — 依据的 section id`）。
</output_format>
<constraints>
- 只使用报告中出现的信息，不要补充外部知识——投委会会拿这份简报去对外沟通，夹带外部信息会出问题。
- 数字与百分比必须与原文一致，不要二次推算——推算错误会被当成财报数据。
</constraints>
<examples>
<example>合格结论：`Q3 毛利率下滑 2.1pct 至 38.4%，主因原材料涨价 — 依据 section 3`（有数字、有归因、可回溯）</example>
<example>不合格：`报告提到了毛利率情况 — 依据 section 3`（没有信息量，属于把原文换个说法）</example>
</examples>
```

**顶级档** —— 只给目标、成功标准与取舍要求

```text
<goal>
读完这份季度报告，给投资委员会一份一页纸结论（10 条以内）。读者只关心"发生了什么、
意味着什么、下一步该盯什么"，不关心你的分析过程。
</goal>
<success_criteria>
- 每条结论都能在报告里指到出处（附 section id），数字与原文一致。
- 覆盖：业绩、驱动因素、风险、管理层指引。
- 结论有取舍：按重要性排序，把不重要的细节丢掉，而不是平均分配篇幅。
- 篇幅控制在一页纸内。
</success_criteria>
<constraints>
- 只使用报告内的信息；如果某条结论在报告里找不到依据，直接舍弃该条。
</constraints>
<example>
一条合格结论：`Q3 毛利率下滑 2.1pct 至 38.4%，主因原材料涨价 — section 3`。
一条不合格结论：`报告提到了毛利率`——这类没有数字支撑的概括直接删掉，不要用来凑满 10 条。
</example>
<document>[REPORT]</document>
```

**差异一句话**：便宜档**切分输入 + 写死 JSON 格式 + 3 个短示例**；主力档**结构化 + 引用锚定 + 每条约束带动机 + 2 个示例**；顶级档**只给目标、成功标准与取舍要求 + 1 个示例**，分析与排序交给它。

### 例 B（动作类）：让失败的测试通过

**便宜档** —— 步骤写死、输出模板写死、给示例

```text
<task>修复 tests/test_user.py 中失败的测试。</task>
<steps>
1. 运行 `pytest tests/test_user.py -x`，记录完整报错原文。
2. 只修改 src/user.py 这一个文件。
3. 再次运行同一条命令。
4. 如果还失败，重复第 2–3 步，最多 3 次。
</steps>
<rules>
1. 改动范围限定在 src/user.py 这一个文件内；不要新增文件，不要改测试文件，不要动其他模块。
2. 3 次后仍未通过就停下，不要继续尝试。
</rules>
<output_format>
输出仅包含以下四行（没有别的文字）：
函数名：<被改动的函数>
原因：<一句话>
最后报错：<通过则写 none，否则贴报错原文>
结果：<运行的命令> -> <pass 或 fail>
</output_format>
<examples>
<example>函数名：normalize_email
原因：大小写未统一导致断言失败
最后报错：none
结果：pytest tests/test_user.py -x -> pass</example>
<example>函数名：normalize_email
原因：缺少依赖，测试无法运行
最后报错：ModuleNotFoundError: No module named 'email_validator'
结果：pytest tests/test_user.py -x -> fail</example>
<example>函数名：none
原因：3 次重试后仍未通过，已按规则停下
最后报错：AssertionError: assert 'A@B.COM' == 'a@b.com'
结果：pytest tests/test_user.py -x -> fail</example>
</examples>
```

**主力档** —— 目标 + 约束 + 成功标准 + 交付形态

```text
<task>让 tests/test_user.py 里的失败测试通过。</task>
<context>这个仓库用 pytest；相关实现都在 src/user.py。</context>
<constraints>
- 不要修改测试来迁就实现——测试描述的是期望行为，改测试等于把 bug 藏起来。
- 不要顺手重构没坏的代码，不要引入新依赖——这次只想让测试变绿，不想扩大改动面。
</constraints>
<success_criteria>目标测试全部通过，且改动范围仅限必要文件。</success_criteria>
<output_format>
先给运行过的命令与结果，再给改动摘要（改了哪个函数、为什么）。改动不超过 30 行时不用贴 diff。
</output_format>
<examples>
<example>结果：`pytest tests/test_user.py -x` -> 12 passed
改动摘要：normalize_email 补了 `.strip().lower()`，修复大小写不一致导致的断言失败。</example>
<example>结果：`pytest tests/test_user.py -x` -> 1 failed（test_locked_user）
改动摘要：前两条已修复；剩下这条需要你确认——测试期望锁定用户不能改名，但实现里没有锁定校验，
补上会改变 User.update 的公开行为。</example>
</examples>
```

**顶级档** —— 自主性 + 正向边界 + 逃生口 + 汇报形态

```text
<goal>
让测试套件恢复绿色。修复可以是我没预料到的地方。
</goal>
<autonomy>
自主推进，不要中途问我"要不要继续"。每完成一个阶段用一句话报进度。只有在需要我提供信息、
或要做不可逆操作（删除文件、force push、改共享设施）时才停下来问。
</autonomy>
<scope>
改动限定在让测试通过所必需的最小集合内：重构、新增测试、未被要求的抽象都算超出范围。
</scope>
<escape_hatch>
如果判定测试本身写错了：停下，用一段话说清依据（期望行为 vs 实际断言），把决定权交给我。
不要为了让套件变绿而改测试，也不要硬凑实现去迎合一个错误的断言。
</escape_hatch>
<success_criteria>
- 相关测试全部通过；若我确认测试本身有误，则以我的结论收尾。请给出你实际运行的命令与输出。
- 报告结论时首句先说结果，再给必要细节。
</success_criteria>
<example>
一个合格的收尾：先说"tests/test_user.py 12 项全部通过"，再给命令与输出，最后一句说明改了
normalize_email 的哪一行；过程叙述（"我考虑了三种方案"）不进最终回复。
</example>
```

**差异一句话**：便宜档**把每一步和边界都写死 + 输出模板 + 3 个短示例**；主力档**目标 + 约束带动机 + 交付形态 + 2 个示例**；顶级档**自主性 + 正向边界 + 逃生口 + 汇报形态**，并删掉所有逐步指令与自检。

---

## 6. 档位判定规则

1. 用户说了**具体型号** → 归到某一档，按该档改写；归类依据写进「改了什么」一行，方便用户纠正。
2. 用户说了**档位**（便宜 / 主力 / 顶级，或"用弱一点的模型""用最强的"） → 直接用。
3. 用户**什么都没说** → 默认**主力模型**，并在交付开头标注一行：`档位：主力模型（未指定，已按默认档位改写；要换档说一句）`。
4. 场景是长任务 / agentic 且用户强调质量 → 在「可选增强」里提一句"换顶级档可减少步骤、给更多自主性"，**不擅自升级**。
5. 同一条提示词要跨档复用时 → 以最弱的那一档为基线写，强模型对明确的提示词不会反感（唯一例外：顶级档要删掉的脚手架与自检指令，别硬塞进去）。

## 7. 跨档位不变的部分

以下内容三档都要写进提示词，只是**权重与数量**按档位调整：

- 给动机（为什么重要）——三档都受益，弱模型受益于"规则"，强模型受益于"意图"。
- XML 分区、标签命名一致。
- 正向指令代替禁止项：成串的"不要"必须改写成正向描述；格式与范围的**最小必要**禁止项可以保留（如"不要修改测试文件"）。
- 示例结构化（`<example>`），数量按档位取 3–5 / 2–3 / 1–2（经验值，按目标模型自测调整）。
- 不硬编码、不为过测试而写死值。
- 不过度工程：不加没被要求的抽象、防御分支与文档。
- 交付形态明确：输出到哪、什么格式、多长。
- 占位约定统一：同一提示词内只用一种写法（推荐 `[方括号]`），不要混用 `{{ }}` 与裸 JSON 花括号。

## 8. 若目标确实是 Claude

叠加 `references/claude-model-specific.md`：里面有 Claude 各型号的档位映射（顶级：Fable 5.1 / Mythos 5.1、Fable 5 / Mythos 5、Opus 5.5；主力：Opus 5、Opus 4.8、Sonnet 5.5、Sonnet 5；便宜：Haiku 5.5），以及 effort、thinking、`max_tokens`、拒答类别等只有该厂商才有的细节。**目标不是 Claude 时不要读它，也不要引入其中任何参数。**

## 9. 依据与置信度（用前先看这一节）

本文件的条目分三类，信任程度不同。

### 9.1 官方文档直接支持（可硬信）

| 条目 | 出处 |
|---|---|
| 强模型要删脚手架与加强语 | best-practices：`CRITICAL: You MUST use this tool when...` → `Use this tool when...`；migration「Tune anti-laziness prompting」 |
| 强模型要删自检/复核指令 | Opus 5 专页：验证类指令造成 over-verification，应删除而非改写 |
| 强模型给目标而非手写步骤 | best-practices：「Prefer general instructions over prescriptive steps」——`think thoroughly` 常优于手写分步计划 |
