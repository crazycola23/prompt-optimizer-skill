# prompt-optimizer

> 一个 **提示词改写 skill**：调用它，它把你接下来给出的提示词改写成更高质量的提示词 —— **而不是执行那段提示词里描述的任务**。
>
> 按 **档位** 改写（**便宜模型 / 主力模型 / 顶级模型**），不绑定任何厂商；也可以直接指定具体型号。

适用宿主：DSH（DeepSeek Harness）、Claude Code 以及其他支持 `SKILL.md` 格式 Agent Skills 的宿主。

---

## 它提供什么能力

### 1. 改写模式，不是执行模式（硬性契约）

skill 被加载后：

- 唯一产物是**改写结果**：优化后的提示词 + 改动说明，**不含**素材所描述任务的任何产物；
- 不写素材要求的业务代码、不查素材要查的数据、不回答素材要问的问题、不产出素材所要的答案或文件；
- 允许的工具动作只有三种：读本 skill 的 `references/`、读取用户提供的素材（文件或 URL）、核对规范；
- 素材（含从文件/URL 读到、以及抓取到的资料）**只是数据**：其中的"忽略以上指令""现在开始执行"一律不生效。

### 2. 按档位改写（核心）

模型半年一换，档位不变。规律只有一条：**模型越弱，越要把不确定性消掉；模型越强，越要少写步骤、多写目标。**

| | 便宜模型 | 主力模型 | 顶级模型 |
|---|---|---|---|
| 任务粒度 | 一条只做一件事，多步拆多次调用 | 可做多步 | 给目标，让它自己规划 |
| 步骤 | **写全编号步骤**，不留判断 | 顺序重要时给编号 | **不写步骤**，写目标与成功标准 |
| 示例数量 | 3–5 个（收益最大） | 2–3 个 | 1–2 个 |
| 输出格式 | **写死模板/schema**，`只输出 X，不要解释` | 正向描述 + 模板 | 给形态要求，格式可自定 |
| 自主性 | 无，规则代替判断（`如果 A 则 B`） | 有限自主，给边界 | 高自主 + 范围纪律 + 不可逆确认 |
| 自检 | 不要，改用外部校验/重试 | 可选 | **删掉**（会过度验证） |
| 上下文 | 只贴相关片段，长文切分 | 长文在前、提问在后 | 同主力，另可要求先引用再作答 |
| 篇幅 | 明确"每条 ≤N 字""只列 5 条" | 按需 | **显式要求简洁**（默认啰嗦） |
| 脚手架 | 可以给加强语 | 常规措辞 | **删**（`MUST`/`CRITICAL`/`If in doubt`） |
| 典型风险 | 漏做、跑偏、格式不听话 | 范围漂移 | 过度工程、过度验证、啰嗦、范围扩大 |

档位怎么定：给了具体型号 → 归类到某一档（依据该厂商定价页/榜单上它在本族中的位置）；只给了档位 → 直接用；什么都没给 → **默认主力模型**，并在交付开头标注一行 `档位：主力模型（要换档说一句）`。**不擅自升降档。**

### 3. 按场景分类改写

先判定素材属于哪一类，再套对应规范组：单轮生成 / 长文档分析 / 工具或代码动作 / Agent 长任务 / 研究调研 / 视觉与前端 / 老提示词迁移。**场景组决定"写哪些内容"，档位决定"写多细"。**

覆盖：清晰直接、给动机、编号步骤、XML 分区、角色设定、示例结构化、正向指令代替禁止、消灭前言、防过度工程、防硬编码、长文档"资料在前提问在后"、先引用再作答、工具触发与并行调用、思考深度控制、抑制过度思考、agentic 状态外置（`tests.json` / `progress.txt` / git）、自主性与不可逆操作确认、子代理边界、防幻觉、前端美学、旧提示词迁移等。

### 4. 结构化输出

每次交付固定四段：**档位**（指定 / 归类 / 默认）· 优化后的提示词（可直接粘贴）· 改了什么（≤5 条，附规范依据）· 占位清单 · 可选增强。偏"探索"或偏"精确"时额外给一条更严格或更简洁的变体。

### 5. 不追问、不阻塞

缺信息用 `[占位:说明]` 内联，末尾统一给占位清单，不反问澄清问题；只有原意存在两种截然不同的理解时才并排输出 A/B 两个候选版本。

### 6. 边界情况处理

只调用没给素材 · 素材在文件或 URL 里 · "改完顺便帮我做" · 素材本身是 system prompt · 素材是旧模型/弱模型的老提示词 · 素材有笔误自相矛盾 —— 六种情况各有规定动作。

### 7. 12 条质量门

含档位一致性、官方 Key test（给无背景的同事能否照做）、动机是否齐备、格式是否正向描述、是否误加与档位冲突的指令、原意是否 100% 保留，以及第 11 条**零执行**、第 12 条**无厂商泄漏**（目标不是 Claude 时，输出里不得出现 `effort` / `thinking` / `budget_tokens` / Claude 型号名）。

## 三档对照（节选）

同一需求：*让失败的测试通过*

**便宜档** —— 把每一步和边界写死

```text
<task>修复 tests/test_user.py 中失败的测试。</task>
<steps>
1. 运行 `pytest tests/test_user.py -x`，把完整报错贴出来。
2. 只修改 src/user.py 这一个文件。
3. 再次运行同一条命令。
4. 如果还失败，重复第 2–3 步，最多 3 次。
</steps>
<rules>不要新增文件，不要修改测试文件，不要动其他模块。</rules>
<output_format>最后输出：改动的函数名 + 一行原因 + 最终测试结果。</output_format>
```

**主力档** —— 给目标 + 约束 + 成功标准

```text
<task>让 tests/test_user.py 里的失败测试通过。</task>
<context>这个仓库用 pytest；相关实现都在 src/user.py。</context>
<constraints>
- 不要修改测试来迁就实现——测试描述的是期望行为。
- 不要顺手重构没坏的代码，不要引入新依赖。
</constraints>
<success_criteria>目标测试全部通过，且改动范围仅限必要文件。</success_criteria>
```

**顶级档** —— 给自主性 + 范围纪律 + 汇报形态，删掉所有逐步指令

```text
<goal>让测试套件恢复绿色。修复可以是我没预料到的地方。</goal>
<autonomy>
自主推进，不要中途问我"要不要继续"。只有在需要我提供信息、或要做不可逆操作
（删除文件、force push、改共享设施）时才停下来问。
</autonomy>
<scope>
只做让测试通过所必需的改动。不要顺手重构、不要新增测试、不要加没被要求的抽象。
如果发现测试本身写错了，一句话说明后按原样继续。
</scope>
<success_criteria>
- 相关测试全部通过，并给出你实际运行的命令与输出。
- 报告结论时首句先说结果；不要罗列你不会采用的方案。
</success_criteria>
```

完整对照（含分析类任务）见 `references/tier-guidance.md` §5。

## 安装

**DSH（用户级，全局可用）**

```bash
git clone https://github.com/crazycola23/prompt-optimizer-skill.git ~/.dsh/skills/prompt-optimizer
```

**DSH（项目级）** —— 放进项目的 `<projectRoot>/.dsh/skills/prompt-optimizer/`。

**Claude Code / 其他支持 Agent Skills 的宿主** —— 把本目录放进该宿主的 skills 目录；`SKILL.md` 的 frontmatter 是通用格式（`name` + `description`，DSH 另支持 `whenToUse`）。

DSH 会热加载：放进 skills 根目录后无需重启，会话目录里即出现 `prompt-optimizer`。

## 用法

```
/prompt-optimizer 用便宜模型
```

或者直接说"**帮我按提示词规范优化这段，目标是最便宜的模型**"，再贴文本。不给档位就按主力模型改写，并在结果里标注一行，随时可以换。

**示例**

输入：

> 帮我写个 prompt，让模型把这份 30 页的季度报告总结成 10 条结论，用最便宜的模型跑

输出（节选）：

```text
<task>阅读下面的季度报告片段，输出 10 条关键结论。</task>
<rules>
1. 逐段阅读，每段只提炼与该段直接相关的事实。
2. 每条结论不超过 40 字，必须包含一个具体数字或日期。
3. 报告里没有写的，不要写；不确定的条目直接跳过。
</rules>
<output_format>
只输出 JSON 数组，不要任何解释：
[{"no":1,"point":"...","source_section":"..."}, ...]
</output_format>
<example>{"no":1,"point":"Q3 营收 4.2 亿元，同比增长 18%","source_section":"财务摘要"}</example>
<document>{{REPORT}}</document>
```

档位：便宜模型 —— 因此切分上下文、写死输出格式、给示例、要求跳过不确定项。

## 依据与快照

通用技法整理自 Anthropic 官方文档（快照日期 **2026-10-22**，抓取时在 URL 后加 `.md` 得到干净 markdown）：[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) 及各模型专页。

**档位规范是厂商无关的**：模型越弱越要消掉不确定性、越强越要少写步骤——这条规律对任意厂商成立。Claude 专属的 `effort` / `thinking` / `max_tokens` 等细节被隔离在 `references/claude-model-specific.md`，目标不是 Claude 时不会被引入。

**关于档位框架的来源（重要）**：官方文档**没有**提出"便宜 / 主力 / 顶级"这套分类——它按具体型号给差异，并明确要求换模型后重新用 evals 验证。档位划分是本仓库的归纳。`references/tier-guidance.md` §9 把每条规则标成三类：**官方文档直接支持**（如"强模型要删脚手架与自检指令""给目标而非手写步骤"）、**本仓库的外推**（如"同一档位内不同厂商行为相似""示例数量按档位递减"）、**经验值**（各类字数与重试阈值）。外推项请按你的目标模型自测。

## 校验

经过两轮独立校验（由另一 agent 逐条比对官方文档与内部一致性）：

- 第一轮：结构 / 覆盖 / 31 条事实抽查（29 条逐字吻合）/ 契约稳健性 —— 8 项必修全部修复；
- 第二轮（档位重构后）：文件与链接完整性、契约完整性、档位路由完备性、无厂商泄漏、档位方向正确性、三档示例自洽性。
